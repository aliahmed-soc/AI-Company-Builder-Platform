# ADR-022 — Authentication Provider

1. **Title:** Clerk for MVP authentication and account/session management; platform backend remains the authorization authority
2. **Status:** Accepted
3. **Date:** 2026-07-18
4. **Owner:** Product owner
5. **Context:** AOQ-05 asked how ACC-001/002 authentication is delivered. ADR-007 (accepted) makes internal membership the tenant authority; NFR-002 requires server-authoritative authorization; invariant 2 forbids client-supplied tenant authority.
6. **Decision:** **Clerk** provides: user registration; sign-in; session management; account identity; organization membership **primitives where useful**; initial role and permission **claims**; organization-switching UI where appropriate.
7. **Scope:** Identity and session layer only.
8. **Explicit boundaries — the critical rule:** Clerk authenticates users and supplies identity context. **The platform backend remains authoritative for company membership, resource authorization, approval authority, and tenant-owned data access.** Required flow on every protected operation: `Authenticated Clerk user/session → internal user mapping → internal account/company membership → internal role and permission check → tenant-scoped database authorization (ADR-007) → operation-specific policy and approval check (ADR-009/010)`. Access is **never** granted merely because the client supplied a company ID, a Clerk organization ID, a role string, an active-organization value, or hidden UI state. Clerk organizations **may map to platform accounts**, but a **company remains a product-owned domain entity** and is never reduced to a Clerk object. Approval decisions derive authority from internal roles only (invariant 5 unaffected by Clerk claims).
9. **Alternatives considered:** Auth library + own session store (full control, more security surface to build/maintain in Phase 1); other managed IdPs (comparable; Clerk selected by owner for organization primitives + speed); enterprise SSO providers (post-MVP concern, PRD §20).
10. **Positive consequences:** Phase 1 velocity; hardened session handling; organization primitives accelerate account/membership UX without owning it.
11. **Negative consequences:** Third party in the authentication path; webhook-driven state synchronization to maintain; per-MAU cost.
12. **Security implications:** Clerk joins the subprocessor register (ADR-005); session verification server-side on every request; internal authz negative tests (NFR-002) explicitly include forged Clerk-claim scenarios; tenant isolation (launch gates 1/2) is tested **below** Clerk — Clerk compromise must not equal tenant-data compromise.
13. **Operational implications:** **Outage behavior:** Clerk unavailability ⇒ new sign-ins fail honestly; existing verified sessions may continue per session-verification mode chosen at implementation; autonomous/queued work (which authenticates via internal machine context, not Clerk) continues unaffected. **Webhook synchronization:** user/org events sync to internal mappings via signature-verified webhooks with idempotent, replay-safe consumers (event-id dedupe per EVENT-CATALOG envelope rules); reconciliation job detects drift. **Account-deletion synchronization:** Clerk deletion events trigger the internal ACC-005 flow (two-step, retention-honoring) — deletion is governed by platform rules, not silently by IdP state.
14. **Portability implications — identity-provider replacement boundary:** all authorization data (users mapping, memberships, roles) lives in platform tables; Clerk supplies only identity assertions. Replacement = swap the identity adapter + migrate credentials/sessions; authorization model untouched.
15. **Reversal cost:** Medium — identity adapter + user migration; bounded by the internal-mapping design.
16. **Requirement IDs:** ACC-001, ACC-002, ACC-003, ACC-004, ACC-005, ADMIN-003, NFR-002, NFR-001, PORT-003.
17. **Governing architecture ADRs:** ADR-007 (tenant authority), ADR-006 (identity module), ADR-009 (approval actor rules), ADR-005 (subprocessor documentation).
18. **Follow-up work:** AOQ-23 select social-login methods; AOQ-24 webhook synchronization strategy detail (ordering, backfill, drift reconciliation cadence); session-verification mode selection; forged-claim negative test suite.
19. **Review triggers:** Clerk incident/pricing change; enterprise SSO requirements (future segment); MAU cost crossing build-vs-buy threshold; webhook drift incidents.
